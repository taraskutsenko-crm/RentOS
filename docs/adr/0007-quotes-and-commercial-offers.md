# ADR 0007: Quotes and Commercial Offers

**Status:** Accepted
**Date:** 2026-07-29

## Context

TASK-0007 adds a commercial-offer layer in front of the Rentals module:
staff prepare a Quote (assets, generic products/services, discounts, tax,
deposits, terms), send it to a customer over a secure public link, the
customer accepts or rejects it, and an accepted Quote converts into a real
Rental. This ADR covers the handful of decisions with the widest blast
radius — several of which deliberately touch, but do not modify, the
already-shipped Rentals module.

## Decision

### QuoteItem is its own model — never a variant of RentalItem

`RentalItem.assetId` is a required foreign key, and `AvailabilityService`,
`RentalsService.assertAssetsRentable`, and `syncAssetStatuses` all assume
every rental line is a real, physical asset. A Quote must also support
non-asset lines (`SERVICE`, `PRODUCT`, `FEE`, `DELIVERY`, `COLLECTION`,
`LABOR`, `CUSTOM`) — rather than loosen `RentalItem`'s required `assetId`
(a change to shipped, tested code, for a feature that doesn't need it),
`QuoteItem.assetId` is nullable from the start, on a brand-new model with
no existing callers to break. `QuoteBillingMode` is a superset of
`RentalBillingMode` (`DAILY`/`WEEKLY`/`MONTHLY`/`CUSTOM`, plus `FLAT` =
`unitPriceMinor × quantity`, no duration factor) — `FLAT` is available to
every item type except `ASSET` (enforced in `QuotesService`, not the
database), since an asset booking must map onto one of `RentalItem`'s four
existing billing modes at conversion time.

### Conversion copies only ASSET items into RentalItem rows; the Rental's totals are copied from the Quote, not recomputed

A Rental's `RentalItem[]` can only ever represent physical assets (see
above). So when converting an accepted Quote:

- Only `QuoteItem`s with `itemType = ASSET` become `RentalItem` rows.
- The created Rental's `subtotalMinor`/`discountMinor`/`taxMinor`/
  `totalMinor` are copied **verbatim** from the Quote's own authoritative
  totals — which include every item type — rather than recomputed via
  `computeRentalTotals` over just the asset items. This guarantees the
  Rental's total always equals what the customer actually accepted, even
  though its `RentalItem` rows alone would sum to less.
- The full itemized breakdown (including every non-asset line) remains
  permanently visible on the immutable source Quote, reachable from the
  Rental via `Rental.sourceQuoteId` (nullable, unique, additive — zero
  impact on any Rental created directly).
- A quote with zero `ASSET` items cannot be converted (`400` — mirrors
  `RentalsService.reserve()`'s "cannot reserve with no items" rule, since
  a Rental with no `RentalItem` rows isn't a meaningful booking).

Conversion builds the Rental and its `RentalItem`/`RentalStatusHistory`
rows directly inside `QuotesService.convertToRental`'s own `$transaction`,
rather than calling `RentalsService.create()` (which owns its own
transaction boundary and computes totals purely from its own items — using
it here would either break atomicity across two services' transactions or
require changing its behavior). This duplicates a small amount of insert
logic but keeps "revalidate → create → link → mark `CONVERTED`" atomic,
which the task requires explicitly. Numbering reuses
`generateRentalNumber`, extracted verbatim from `RentalsService` into
`apps/api/src/rentals/rental-numbering.util.ts` so both call sites share
one implementation.

### Numbering: a real atomic sequence, not the existing count-then-check pattern

`Rental.rentalNumber` is generated by counting existing rows and probing
candidates for a free one (`RentalsService`'s `generateRentalNumber`) — a
genuine, pre-existing concurrency gap (two simultaneous transactions can
compute the same candidate; the loser's insert throws an uncaught
`P2002`). Quotes needed something better: a new `QuoteSequence` model
(`tenantId`, `year`, `lastNumber`), incremented via a single Postgres
`INSERT ... ON CONFLICT (tenantId, year) DO UPDATE SET lastNumber =
lastNumber + 1 RETURNING lastNumber` inside the same transaction as the
Quote row itself. `ON CONFLICT DO UPDATE` takes a row-level lock, so two
concurrent transactions incrementing the same counter are correctly
serialized by Postgres — never racing. The counter only ever increases, so
a cancelled or deleted quote's number is never reused. Format:
`Q-<year>-######` (year = `issueDate`'s **UTC** year, timezone-safe).
`generateRentalNumber`'s existing race is deliberately left unfixed —
out of scope for this task.

### Decimal-safe arithmetic: integer minor units + integer basis points, no new library

The task requires "decimal-safe arithmetic, never floating point." This
codebase's existing convention (ADR 0002) is integer minor currency units
with no `Decimal`/float anywhere — Quotes extends this rather than
introducing `decimal.js`: percentages (`discountValue` when
`discountType=PERCENTAGE`, `taxRateBp`) are integer **basis points**
(2000 = 20.00%), and every derived amount is computed with exactly one
`Math.round(base * rateBp / 10000)` per line — never chained or
accumulated. This is the same integer-cents-plus-basis-points approach
payment processors like Stripe use, and gives the same correctness
guarantee a Decimal library would, without a new dependency the codebase
has deliberately avoided everywhere else. `resolveDiscountMinor` clamps to
`[0, baseMinor]` so a discount can never exceed or invert the amount it
discounts.

Quote-level totals mirror `computeRentalTotals`'s shape:
`subtotalMinor` = sum of item line totals (each already net of its own
discount + tax); the quote-level discount is one more flat-on-top layer,
exactly like `Rental.discountMinor`; `taxTotalMinor` is a display
aggregate of every line's own tax (already folded into `subtotalMinor`,
never added twice); `depositTotalMinor` is a display aggregate only,
excluded from `totalMinor` — matching how `RentalItem.depositMinor` is
never folded into `Rental.totalMinor` either.

### PDF generation: `pdfkit` + an embedded Unicode font, not a headless browser

No PDF library existed in this codebase. `pdfkit` (pure JS, no Chromium
dependency) was chosen over `puppeteer` (a real Docker/CI reliability
risk — a Chromium sidecar is heavier, slower, and more failure-prone in
constrained containers) and over `@react-pdf/renderer` (would introduce
React into an otherwise React-free NestJS backend). pdfkit's built-in
Helvetica/Times/Courier fonts only cover Latin-1, which would silently
break `ru`/`uk` (Cyrillic) quotes — the `dejavu-fonts-ttf` npm package
(a normal, license-clear dependency; no ad-hoc file download) ships real
`.ttf` files with full Cyrillic and Latin-Extended coverage, embedded via
`doc.registerFont()`. Verified by rendering real sample PDFs (Cyrillic
content, 25+ line items forcing multi-page output) and round-tripping
them through `pdf-parse` in the test suite — this caught two real
pdfkit pitfalls during development, now covered by regression tests:

1. Writing footer text inside the bottom margin band via the normal
   `.text()` flow makes pdfkit think the page overflowed and silently
   inserts extra blank pages per call — fixed by zeroing
   `doc.page.margins.bottom` for those two calls only.
2. Explicit two-column `x` positioning (used for the totals table) leaves
   `doc.x` at the last column's position; a later `.text()` call that
   omits an explicit `x` silently inherits that offset, shrinking its
   wrap width and clipping long text — fixed by resetting `doc.x` back to
   the page margin afterward.

PDF labels are localization-aware via a small `pdfLabel()` resolver that
reads `quote.pdf.*` from `@rentos/localization`'s shared resources (now a
dependency of `apps/api` too) for the tenant's `defaultLanguage`, falling
back to English — a single source of truth for translated strings shared
with the frontend, rather than a second hardcoded copy in the backend.
Binary output goes through the existing `StorageService` (ADR 0005,
unmodified); a `QuoteDocument` row is created per generation (never
overwritten), so `GET .../pdf` always serves the most recent one without
regenerating on every request, while `POST .../pdf` forces a fresh one.

### Email: a new `EmailModule` mirroring `StorageService`'s swappable-adapter pattern exactly

No email/SMTP library or abstraction existed. `EmailModule` copies
`StorageService`'s proven shape precisely: an `EmailProvider` interface, an
`EMAIL_PROVIDER` DI token, and a default `LoggingEmailProvider` that logs
via Nest's `Logger` and always reports `{ success: true }` — a deliberate,
honest placeholder until a real SMTP/SES/SendGrid provider is wired in via
a different `useClass`/`useFactory`, with zero changes needed to any
caller. The email send happens **after** the status-change transaction
commits, never inside it — an SMTP/API call is network I/O and must not
hold a database transaction open. A failed send is recorded via an audit
log entry (`quote.send_email_failed`) without rolling back the `SENT`
status, and `emailSent`/`emailError` in the `send` response honestly
reflect what actually happened — never a fabricated success.

### Public acceptance: a hashed token on the Quote row, no separate token table

Mirrors `RefreshToken`'s exact precedent (`node:crypto`'s
`randomBytes(48).toString("base64url")` for the plaintext, SHA-256 for the
stored hash — the same reasoning applies: this is a high-entropy random
value looked up by exact hash, not a low-entropy secret needing
deliberately slow hashing). `Quote.publicTokenHash` + `publicTokenExpiresAt`
are two columns on the Quote itself, not a separate table — one active
token at a time is sufficient (no per-recipient tracking requirement
exists), and it's regenerated (overwriting the old hash) on every `send`.
Public routes resolve purely by hashing `:token` and querying
`{ publicTokenHash, publicTokenExpiresAt: { gt: now }, status: { not:
CANCELLED } }` — no `tenantId` in the URL, since a valid 256-bit-plus
random hash can only ever match the one quote it was generated for.
`@Public()` (exempting the global `JwtAuthGuard`) plus a tightened
`@Throttle()` (the existing `@nestjs/throttler`, already a dependency)
guards against scraping/brute-force. The public response
(`PublicQuoteView`) is a hand-picked field subset that never includes
`internalNotes`, `tenantId`, user ids, or the token hash. Acceptance is
explicitly labeled "quote acceptance," with a visible disclaimer that it
is not a qualified electronic signature — this codebase has no compliant
e-signature architecture, and the task explicitly asked not to imply one.

### Revisions: duplication only, no revision-chain fields

The task explicitly asked not to overengineer revisions if they'd
destabilize the project. `POST /quotes/:id/duplicate` creates a fresh
`DRAFT` copy (new number, cleared acceptance/rejection/conversion
metadata, items and terms copied, totals recomputed under current rules)
plus a single nullable `Quote.duplicatedFromQuoteId` self-relation for
lineage. The rejected alternative — explicit `revisionNumber`/
`previousQuoteId`/`rootQuoteId` fields with a full revision-chain
UI — was judged unnecessary complexity for what "always duplicate instead
of mutating a sent/decided quote" already achieves; `PATCH` itself already
enforces immutability of commercial fields once a quote leaves `DRAFT`.

## Consequences

- Quotes introduces five new tables (`Quote`, `QuoteItem`,
  `QuoteStatusHistory`, `QuoteDocument`, `QuoteSequence`) and one additive
  column on `Rental` (`sourceQuoteId`) — zero schema changes to
  `RentalItem`, `AvailabilityService`, or any existing Rentals behavior.
- Two new runtime dependencies: `pdfkit` + `dejavu-fonts-ttf` (PDF
  rendering), plus `pdf-parse` as a dev-only dependency for PDF content
  regression tests.
- `@rentos/localization` becomes a dependency of `apps/api` (previously
  frontend-only), so PDF labels share the same translation source as the
  UI instead of duplicating strings.
- `RentalsService.generateRentalNumber` was extracted into a standalone,
  behavior-identical `rental-numbering.util.ts` — a pure refactor, no
  behavior change, verified by the full existing Rentals test suite
  passing unmodified.
